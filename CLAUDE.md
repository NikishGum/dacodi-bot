## Project Overview

**Telegram Support Bot** — A specialized support system for an infrastructure provider (CDN, SecurityCDN, AI-protection, VPS, Protected DNS, API, Terraform). The bot collects structured information from clients via Telegram and creates tickets in Zoho Desk, enabling operators to respond quickly with full context.

**Core value**: Minimize time between client message and operator response by pre-collecting structured data and creating tickets automatically.

### Key Constraints

- **Single active ticket per client** — new `/start` doesn't restart data collection if a ticket is open; only closed tickets allow new issues
- **Complete client isolation** — each client has their own chat; no cross-chat visibility
- **Minimal bot presence** — bot gathers data only; operator responses and client replies are mirrored, not processed
- **Two-way binding** — operator answers from Zoho sync to Telegram in <3s; client messages become ticket comments
- **Resilience to Zoho outages** — failed ticket creation is queued and retried every 30s in Redis

## Tech Stack

- **Language**: Go 1.22+
- **Telegram**: `github.com/go-telegram-bot-api/telegram-bot-api/v5`
- **Redis**: `github.com/redis/go-redis/v9` (AOF persistence required)
- **HTTP**: Standard `net/http`
- **Logging**: `log/slog` (JSON format)
- **Config**: `github.com/joho/godotenv` + environment variables

## Architecture

```
┌─────────────┐              ┌──────────────────────────────────────┐
│  Telegram   │              │  Infrastructure                       │
│  (webhook)  │──────────────│  • nginx: HTTPS, rate-limit, IP list │
└──────┬──────┘              │  • systemd: auto-restart             │
       │                     └──────────────────────────────────────┘
       ▼
    Supportbot (main)
    ├─ FSM: per-chat state machine (Conversation struct in Redis)
    ├─ Questions: service-specific scripts (cdn, security, ai, server, etc.)
    └─ Webhook: validates token, serializes updates, locks per-chat
       │
       ├─────► Zoho Desk API
       │       ├─ Account lookup (client info + bindings)
       │       ├─ Ticket creation (request → queue if failed)
       │       └─ OAuth2 token refresh (cached 3500s)
       │
       ├─────► Redis (FSM + queue + auth cache)
       │       ├─ fsm:{chat} (conversation state, 24h TTL)
       │       ├─ ticket:{chat} (active ticket mapping, 30d TTL)
       │       ├─ auth:{chat} (cached binding, fast-path auth)
       │       ├─ client:{id} (cached account profile)
       │       ├─ zoho:access_token (OAuth2, 3500s TTL)
       │       └─ queue:tickets (failed request backlog, FIFO)
       │
       └─ Queue worker (background, 30s ticks)
          └─ Retry failed ticket creation from Redis queue

Zoho Desk webhook ──┐
(operator replies)  │
(ticket closed)     └──────► Supportbot webhook handler
                            └─ Routes to Telegram (if reply)
                            └─ Clears active ticket (if closed)

Separate service: tokengen
├─ Generates HMAC-signed binding tokens
└─ Protects client-chat binding (one-time use)
```

### Data Flow for a Support Request

1. **Client sends `/start` with token** (generated by tokengen operator)
   - Bot validates HMAC + expiry (`auth.Manager`)
   - Writes `chat_id` to Zoho account + Redis (`auth:{chat}`)
   - Loads available services from account custom fields
   
2. **Bot asks questions** (FSM in `bot/fsm.go`, state machine in Conversation)
   - For each service, defined question script (cdn, security, ai, server, etc.)
   - Answers collected into `Conversation.Answers` array
   
3. **Client confirms summary**
   - Full description built from answers
   - Priority determined: HIGH if full outage/DDoS, else NORMAL
   
4. **Ticket created in Zoho**
   - Via `zoho.Desk.CreateTicket()` with chat_id in custom field
   - If Zoho is down: request enqueued to `queue:tickets` in Redis
   - Ticket number shown to client
   - State transitions to `StateTicketOpen` (no new `/start` allowed)
   
5. **Operator replies in Zoho** → webhook triggers → reply sent to Telegram
   
6. **Ticket closed** → webhook triggers → client state reset → new `/start` allowed
   
7. **Client message while ticket open** → appended as ticket comment (via polling/webhook handler)

## Key Architectural Decisions

### 1. **Per-Chat Mutex Synchronization** (`bot.chatLock`)
Each chat's FSM updates are serialized with a mutex to handle concurrent Telegram updates safely while allowing different chats to proceed in parallel.

**Why**: Telegram may deliver updates out-of-order or duplicate within a window; mutexes ensure state transitions are atomic per chat without global locking.

### 2. **Redis for FSM State + Retry Queue**
Conversation state (`fsm:{chat}`) and failed tickets (`queue:tickets`) both live in Redis with AOF persistence.

**Why**: Survives restarts; shared storage for distributed workers; fast reads; queue-based resilience decouples Zoho availability from bot responsiveness.

### 3. **Synchronous Webhook Processing**
Updates are processed inside the HTTP handler before returning 200 OK; new updates are queued in Telegram if processing is slow.

**Why**: Preserves message order without an external queue; client sees deterministic state progression.

### 4. **Token-Based Chat Binding** (HMAC with TTL + one-time tracking)
Clients are bound to chats via a short-lived signed token (`bot_client_id | exp | jti | HMAC-SHA256[:16]`), validated on first `/start`.

**Why**: Zoho is source-of-truth for client data; tokens reduce manual chat_id configuration; signature prevents forgery; jti (UUID) prevents replay within window.

### 5. **Bootstrap Allowlist** (`config/clients.json`)
Optional pre-authorized chat IDs for testing without Zoho or tokens.

**Why**: Enables local testing; quick onboarding for test accounts; falls back to Zoho-based auth in production.

### 6. **Retry Queue Instead of Synchronous Retry**
Failed ticket creation is enqueued; a background worker drains the queue every 30s.

**Why**: Doesn't block the webhook on Zoho outages; client gets ticket number (or pending state); automatic recovery when Zoho returns; queued requests survive bot restarts.

## Important Implementation Details

### State Machine (FSM)

**States** (in `bot/fsm.go`):
- `StateIdle` — no active flow
- `StateAwaitingService` — client selecting service from buttons
- `StateAskingQuestions` — bot iterating through service-specific questions
- `StateConfirming` — client confirming answer summary before ticket creation
- `StateTicketOpen` — ticket exists; waiting for operator or close event

**Transitions**:
- `/start` (no open ticket) → StateAwaitingService
- Service selected → StateAskingQuestions (load question script)
- All answers collected → StateConfirming
- Confirmed → CreateTicket (via queue) → StateTicketOpen
- Ticket closed (Zoho webhook) → back to StateIdle
- Open ticket + `/start` → bot reminds of ticket number, stays in StateTicketOpen

### Question Scripts

Each service (`cdn`, `security`, `ai`, `server`, `dns`, `api`, `terraform`) has a hardcoded question set in `bot/fsm.go`. Questions can have:
- **Free text** (no Options) — accepts any reply or media
- **Buttons** (Options set) — inline keyboard with pre-defined choices

Example (cdn service):
```
1. "Опишите проблему" (free text)
2. "Какой домен затронут?" (free text)
3. "Доступен ли origin?" (buttons: Да/Нет/Не знаю)
4. ...
```

### Client Resolution (Registry)

`registry.Registry` resolves `chat_id` → `AccountInfo` (name, services, priority, binding status):

1. **Fast-path**: check `auth:{chat}` in Redis (cached binding)
2. **Fallback**: fetch from Zoho by `cf_telegram_chat_id` custom field + cache.
   Cold-miss full account scans are rate-limited process-wide
   (`ZOHO_SCAN_MIN_INTERVAL`, default 60s) to protect the Zoho API-credit budget
   from unbound strangers; a throttled lookup caches the chat as unknown briefly.
3. **Bootstrap**: check the `CLIENTS_FILE` allowlist (default `config/clients.json`)
4. **Unbound prompt**: an unknown chat is **not** silently ignored — the bot
   greets it and asks for an access key. Any text it sends is then treated as a
   binding token and redeemed (`handleUnboundPrompt` → `handleBinding`).
   Redemption is rate-limited per chat (`maxBindAttempts`), and the limiter
   **fails closed** if Redis is unavailable (a transient-error reply, no binding).

### Zoho Integration

- **OAuth2**: `ZohoRefreshToken` + auto-refresh every 3500s (`zoho/auth.go`)
- **Custom fields** used to bind clients:
  - `cf_bot_client_id` (our stable ID)
  - `cf_telegram_chat_id` (for webhook routing)
  - `cf_bot_services` (available services list)
  - `cf_bot_priority` (**priority floor**: when its value is `HIGH` or `key`,
    case-insensitive, the ticket is forced to High regardless of the per-request
    heuristic; otherwise `detectPriority()` decides — see `finalizeTicket`)
  - `cf_bot_request_id` (optional, `ZOHO_CF_REQUEST_ID`): stores a per-request
    idempotency key written on ticket creation. Unset = idempotency tagging
    disabled (logged at startup).
- **Webhook from Zoho**: two event types
  - Public comment by operator → route to Telegram
  - Ticket closed (status change) → clear active ticket, reset FSM
- **Comment direction & echo-safety**: operator→client uses **public** comments;
  client→operator messages are posted as **private** comments (`isPublic:false`,
  `zoho/desk.go`). This is deliberate — a public client comment would re-trigger
  the "public comment" webhook and echo back to the client. The Zoho webhook rule
  must therefore fire only on **public** comments (i.e. operator replies).
- **Attachments**: client photos/documents from the proof/logs steps are buffered
  as `file_id`s on the conversation, then downloaded from Telegram and uploaded to
  the ticket (`Desk.AddAttachment`, multipart) right after the ticket is created
  (both in the synchronous path and the retry worker).

### Retry Queue Resilience

If `zoho.Desk.CreateTicket()` fails:
1. Request marshaled to JSON and pushed to `queue:tickets` FIFO
2. Worker wakes every 30s, pops from queue, retries
3. If still fails: re-enqueued, worker sleeps to avoid spin-loop
4. If success: ticket number cached, client notified on next webhook reply
5. Queue persists in Redis AOF, survives bot restarts

## Known Limitations & Future Improvements

1. **Question scripts are hardcoded** — could be loaded from Zoho or a database
2. **No multi-language support** — currently Russian only
3. **No rate-limiting inside bot** — relies on Nginx
4. **Ticket fields are fixed** — customization requires code changes
5. **Chat binding is one-way** — no "unbind" endpoint yet
6. **No admin dashboard** — operators manage via Zoho directly

## Testing Notes

- No external test framework used; code relies on logical isolation (mocks via interfaces in tests if added)
- To test webhook signature validation: modify `telegramSecretHeader` check in `bot.WebhookHandler()`
- To test Zoho failure recovery: stop Redis or simulate a 500 from Zoho, watch queue grow
- To test FSM state transitions: trace `fsm:{chat}` in Redis through the conversation flow
